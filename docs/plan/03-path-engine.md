# Phase 3 — Placement, Learning Path, Mastery Gates, Spaced Repetition

Depends on: Phases 0, 1. Can run in parallel with Phase 2.

> Reference implementations already exist and are done in the released skills (`startPlacementQuiz`, `submitPlacementQuizStep`, `designLearningPath`, `validateLearningPath`, `submitNodeQuizAttempt`, `computeNextSpacedRepetition`, `getDueSpacedRepetitionNodes`). The tasks below are the **DB-backed, multi-user port** of those, plus the grading and idempotency parts the skills don't cover.

## T3.1 Difficulty scale & subject lifecycle — `src/lib/lms/subjects.ts`
- `createSubject` (slug generation + uniqueness, `difficulty_scale_n` 1..N, default status `researching`).
- Status transitions: `researching → placement → active → completed`, guarded (e.g. cannot enter `placement` with zero validated sources or without a placement quiz bank).
- `getOverview(ownerId, slug)`: counts, progress, due reviews. All numbers are computed, never stored or hard-coded.

## T3.2 Placement — `src/lib/lms/placement.service.ts`
- `placementStart(subject)`: requires a quiz bank covering the tiers (`lms_quizzes` with `quiz_purpose='placement'`, one or more per tier, generated by the agent via `lms_generate_quiz`). Returns `mid` and the question for it. Persist `low/high/current_mid` in `lms_placement_sessions`.
- `placementSubmitStep(sessionId, submission)`: grade → `stepBinarySearchPlacement` → persist bounds and append history. On completion set `resolved_level`, `subjects.entry_difficulty_level`, status `active`, and mark nodes with `difficulty_level < entry` as `mastered_by_placement`.
- Idempotency: replay of the same step (same question id) returns the stored result and does not move the bounds twice. Reject a submission for a question that is not the current `mid`.
- If a tier has no question, return a typed error telling the agent to generate it (do not silently skip).
- A new session may be started again (retake), which supersedes the old one.

## T3.3 Grading — `src/lib/lms/grading.ts`
Common interface `grade(quiz, submission) → {passed, score, feedback}`:
- `mcq_4`: deterministic; the correct option **never leaves the server** (strip from the payload sent to UI/agent until after submission. The demo marks `correctOption` in the DOM; do not copy that).
- `open_ended`: rubric LLM-as-judge grounded on RAG chunks; interface injected so tests use a stub. Pass threshold configurable.
- `code_challenge` (v1): rubric/LLM review of code plus optional static checks; no execution. (Open question 3.)
- `project_task`: checklist of artifact criteria. v1 is self-attested checklist plus agent review of an optional GitHub commit/diff URL.

## T3.4 Learning path drafting — `src/lib/lms/path.service.ts`
- `draftLearningPath(subject, nodes[], edges[], capstone)`: replaces or merges the node set from `entry_difficulty_level` up in one transaction; nodes below entry are preserved as `mastered_by_placement`. Runs `validatePath` (T0.4) **before commit** and returns defects to the agent. Cap at 3 rounds, then escalate (design state `PAUSED_FOR_USER_PATH_DECISION`; store as `subjects.path_validation` JSON).
- Node study guides: write markdown to `lms/<slug>/nodes/node-NN-*.md` and index it with `node_id` on chunks. Capstone to `lms/<slug>/project/README.md` and `milestones/`.
- Unlock entry nodes (those with no incomplete prerequisites) → `unlocked`; the rest → `locked`.
- `getNextNodes(subject)`: `unlocked | in_progress` plus the top RAG context.

## T3.5 Mastery gate & unlock — `src/lib/lms/quiz.service.ts`
- `generateQuiz` (called by the agent with the content it authored, validated by zod from T0.2): stores the quiz with `prompt_payload`; supports modalities per node.
- `submitQuiz(quizId, submission)` in **one transaction**:
  - `mastery_gate` passed → node `completed`, unlock dependents whose prerequisites are all `completed|mastered_by_placement`, insert `lms_spaced_repetition` (`next_review_at = now + 1d`).
  - failed → node stays `in_progress`; return feedback and targeted RAG excerpts.
  - `spaced_repetition` → T3.6.
- Block gate quizzes for nodes whose status is `locked`. Design §7.1 also says the gate is blocked until the node material is published, so require `github_md_path` set.
- The design's UI says "Requires 100% to unlock"; make the pass threshold a per-quiz field (default: MCQ must be correct).

## T3.6 Spaced repetition service — `src/lib/lms/review.service.ts`
- `dueReviews(ownerId, now)` ordered by `next_review_at`.
- `submitReview` maps the result to grade q (0–5; MCQ: correct → 4, incorrect → 1; open/code: from the score) → `scheduleReview` (T0.4); on lapse set the node flag `needs_refresher` (add to the status check or a boolean column) and return RAG excerpts.
- Review quizzes should be freshly generated variations: `lms_generate_quiz` with `quiz_purpose='spaced_repetition'`, linked to the node. A due review with no pending quiz → agent is told to generate one.
- Retention stat for the header = fraction of reviews passed in a trailing window; show "—" with zero data.

## T3.7 Capstone tracking
Milestone state per node (`project_milestone` text exists; add `milestone_done boolean` or derive from the `project_task` quiz). Overview returns `milestones_done/total`.

## Tests
PGlite integration tests: the full flow create subject → placement (every possible boundary for N=8) → draft path → pass gate → unlock → review pass/lapse. Plus cycle rejected, locked-node quiz rejected, cross-owner access rejected.

## Done when
The whole learner lifecycle works via service functions with a stubbed LLM judge.
